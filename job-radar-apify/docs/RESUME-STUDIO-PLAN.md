Estado: **plan aprobado (2026-08-09), Fase 0 en curso.** Iniciativa separada de
`docs/CV-GENERATION-PLAN.md` (Fases 0-12, ya implementadas) — reusa su bóveda

modelo en dropdown + fixes de performance sobre `CvAdjustOverlay.tsx`) y trajo
su propia especificación detallada (documento externo, `Converted_953e55fd-

hizo en modo plan (3 agentes de exploración + 1 agente de diseño, todos con

hallazgos de auditoría, vive en
`/home/yosman/.claude/plans/ancient-drifting-salamander.md` — este documento
es la versión de seguimiento por fases, en el repo, que se actualiza a medida

## 1. Decisiones ya tomadas por el usuario (no relitigar sin razón nueva)

| Decisión | Elegida | Por qué |

| Alcance de DOCX | **Un solo formato ATS, sin importar la plantilla elegida** | El modelo de Word (secciones/estilos) no mapea limpio al mismo spec declarativo de PDF/preview; un DOCX ATS-safe de una columna es lo que la mayoría de sistemas de reclutamiento necesitan de todas formas. |
| Editor de texto rico (Tiptap/Lexical/etc.) | **No, en ninguna fase** | El modelo `Claim{text, supporting_fact_ids}` valida ids, no procedencia del texto — un editor libre invitaría a que el texto se aleje de lo que el id realmente respalda, sin señal estructural para detectarlo. Se mantienen inputs planos por-Claim (ya existen). Decisión de integridad de datos, no de gusto. |
| Preview en vivo | **HTML/CSS desde `resolveCvDocumentForRender()`, no un viewer de PDF embebido** | Generar PDF en cada tecla sería lento y una dependencia nueva pesada; el HTML/CSS reusa la misma fuente de datos que ya consume el renderer de PDF. |

## 2. Arquitectura — referencia rápida (detalle completo en el plan aprobado)

- **Provider/Model Registry + AI Gateway** (`src/ai-gateway/`): tipos puros
  separados de lo que importa `pg`/`node:crypto`, mismo motivo que ya obligó a
  duplicar una constante entre `quota.ts` y `CvAdjustOverlay.tsx` por el
  import de `pg` en Fase 11 de CV-GENERATION-PLAN.md — evitarlo desde el día
  uno a 10x la escala.
- **Credenciales BYOK cifradas**: tabla nueva `user_ai_credentials`
  (AES-256-GCM vía `node:crypto`, AAD = `user_id:provider_id`, RLS habilitada
  en la MISMA migración que crea la tabla — nunca un follow-up), master key
  nueva `BYOK_ENCRYPTION_KEY`. Nunca se descifra fuera de
  `credential-resolver.ts`, nunca se re-muestra al cliente.
- **Fix de cache key** (`llm_response_cache` gana `user_id`/`provider_id`):
  se hace ANTES de que BYOK tenga su primer proveedor real conectado, no
  después — sin esto, una respuesta pagada con la key de un usuario podría
  servirse a otro.
- **Sistema de plantillas** (`CvTemplateSpec`, declarativo): alimenta tanto el
  preview HTML como una reescritura de `render-pdf.ts` — un mismo spec, dos
  presentaciones. Cambiar de plantilla nunca re-corre el pipeline de IA.
- **Modal Resume Studio**: única dependencia nueva de todo el plan,
  `@radix-ui/react-dialog` (focus-trap/Escape/scroll-lock/ARIA) — el resto se
  hand-rolla siguiendo el patrón ya probado en `CvAdjustOverlay.tsx`
  (`ModelDropdown`, `Field`, `BulletsEditor`, `ReorderHideList`).

## 4. Riesgos activos a vigilar en cada fase

- Scope creep entre fases — cada una tiene un solo criterio de "listo", nunca
  absorber trabajo de la siguiente a mitad de sesión (patrón que ya se vio y
  se corrigió varias veces en `CV-GENERATION-PLAN.md`).
- Pérdida de `BYOK_ENCRYPTION_KEY` (Fase 3) hace irrecuperable cada credencial
  guardada — inherente al diseño, pero necesita el mismo cuidado operacional
  que `DATABASE_URL`/secretos de Wompi.
- Divergencia preview/PDF (Fase 10) es la fuente más probable de bugs
  visibles — checklist de regresión visual obligatorio antes de cerrar esa
  fase.
- Ningún comportamiento default cambia para un usuario existente antes de la
  Fase 13 — el flag y `CvAdjustOverlay.tsx` intacto son la red de seguridad.
